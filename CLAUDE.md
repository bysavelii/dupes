# Как работать в этом проекте

Процесс разработки ведёт Cyberzavod (harness 0.7.1, процесс `default`): Постановка → Код → Ревью → Проверки → Фиксация. Задачу через весь процесс проводит `/feature <задача>`; роли этапов — агенты в `.claude/agents/`.

Проверки проекта не заданы: впиши их в `verification.commands` файла `.cyberzavod/project.json`.

## Архитектура

- Зависимости направлены внутрь: предметная логика не знает о фреймворке, базе, сети и интерфейсе — только о своих типах и интерфейсах.
- Расширение — добавлением, а не правкой по всему проекту: новый вариант — новый член типа или новая реализация интерфейса, ветвление по варианту — исчерпывающее, чтобы пропущенный случай ловил компилятор или тест.
- Абстракция — когда появился второй реальный случай. Не заводить интерфейс, фабрику или параметр «на будущее».
- Один источник правды: одно понятие описано в одном месте, остальные его используют, а не повторяют.

## Объём изменений

- Делай то, о чём задача, и не больше. Замеченное по пути, но не относящееся к задаче, называй в отчёте, а не чини молча.
- Не сохраняй старое ради старого: если изменение делает код ненужным, удали его, без слоёв совместимости, которые никто не просил.
- Небольшие связные коммиты: один коммит — одно законченное изменение, проверки зелёные.
- Развилку, которую не решить по коду и правилам проекта, не решай сам — спроси человека.

## Инженерные принципы

- Код читается как описание того, что он делает: имена из предметной области проекта, без `data`, `item`, `handle`, `process` и без сокращений, кроме общепринятых.
- Одна функция — одно действие. Если функцию нельзя назвать без «и», её надо разделить. Тело читается сверху вниз: сначала ранние выходы, потом основной путь.
- Ошибки не глотаются: их обрабатывают или возвращают с контекстом.
- Без магических значений: числа и строки со смыслом получают имя.
- Комментарий объясняет «почему», когда это не видно из кода. Пересказ кода, закомментированный и мёртвый код не допускаются.
- Новая логика — с тестом рядом. Тест проверяет поведение, а не устройство кода.

## Читаемость кода

Код читают чаще, чем пишут: он должен быть понятен с первого прочтения, расширяться без переделки и выглядеть опрятно. Сначала действуют устоявшиеся правила языка проекта — его стиль-гайд, форматтер и линтеры; правила ниже — сверх них, там, где язык не решает сам.

- Промежуточный результат получает имя. В аргументе вызова — не больше одного вложенного вызова: вместо `toSet(filter(map(list)))` — переменные с именами шагов. Длинная цепочка преобразований разбивается на шаги со смыслом.
- Условие со смыслом получает имя: `isExpired`, а не длинное выражение внутри `if`. Условные выражения не вкладываются друг в друга.
- Пустая строка разделяет смысловые блоки: ранние выходы — от основного пути, подготовку — от действия, многострочный блок — от соседних строк. Плотный текст без пустых строк и пустые строки внутри одной мысли одинаково мешают читать.
- Вложенность — не глубже двух уровней. Глубже — ранний выход или отдельная функция.
- Функция держит один уровень абстракции: либо называет шаги, либо делает работу руками.
- Флаг не переключает поведение функции: два поведения — две функции. Много параметров — один объект с именованными полями.
- Входные данные не меняются: функция возвращает новое значение. Переменная по умолчанию неизменяемая.
- Имена без отрицаний (`isValid`, а не `isNotInvalid`); булевы имена — вопрос с ответом «да» или «нет»: `is`, `has`, `can`.

## Безопасность

- В код, журнал и записи не попадают ключи, токены, пароли, адреса серверов и личные данные.
- Файлы с секретами (`.env` и подобные) не читаются и не правятся.
- Проверки не обходят и не отключают: красная проверка — это работа, а не помеха.
- Необратимое (удаление данных, переписывание истории, публикация) — только с явного согласия человека.
